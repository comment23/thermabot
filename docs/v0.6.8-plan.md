# Thermabot v0.6.8 plan

## Goal

Make the seven-day SHADOW soak reviewable without enabling thermostat writes.

## Scope

- Provide daily UTC counts for sent, simulated, denied, and failed write decisions, grouped by
  outcome, guard, and reason.
- Persist each sampled minute's effective bot state and degradation reason while preserving
  old samples as explicitly untracked.
- Generate a Markdown report from the authenticated, read-only status, health, and shadow APIs.
- Fail the report command on API/schema errors and optionally fail when any sent write is
  recorded.
- Add a responsive command center and shared desktop/mobile shell, visible build version,
  configuration preview/import/export, verified local data backups and documented offline
  recovery. All mutations retain API role checks and CSRF.
- Make HA read outages immediately visible and fail closed until fresh reads succeed.
  Supply an opt-in HA heartbeat-loss package; never install it or enable control implicitly.
- Allow the first administrator (Owner) to be created in the browser, then enter the HA setup
  wizard only when no saved household configuration exists. Existing accounts and saved,
  imported, or legacy configuration must not be overwritten by onboarding.

## Release gate

The code and automated tests do not constitute a real soak. Before publishing v0.6.8:

1. Run the application in SHADOW for seven consecutive days with no sent thermostat writes.
2. Review every DEGRADED interval and any stale rooms; explain or remediate each material
   event.
3. Confirm the report's UTC date and write counts against the application audit data.
4. Record an explicit owner go/no-go. Keep the bot non-ACTIVE until that decision.

If a day is missing, a write is sent, or data cannot be trusted, restart the seven-day window
after investigating; do not treat a partial or untracked history as a passing gate.

## Implementation status

- **Implemented:** per-minute state metadata, daily health aggregates, report CLI, and
  `--assert-no-sent`; responsive dashboard Controls and shared desktop/mobile shell;
  visible version, validated configuration transfer, database backups and HA outage handling.
- **Next candidate:** initial Owner creation with signed browser CSRF, atomic registration
  closure, and configuration-aware wizard navigation. Account creation never starts control.
- **Automated validation:** unit and integration suites, lint, formatting, and strict core
  type-check pass locally.
- **Pending:** live seven-day SHADOW evidence, owner review, and release.

## Controls and recovery behavior

The header now links to Dashboard Controls rather than presenting a single Stop button.
Owners can start/stop and choose Shadow/Active (the existing seven-day gate still applies).
Admins can stop, pause the planned changes, use a temporary override, and toggle guests.
Members see read-only operation guidance. A plan pause does not disable safety restores.
Guest mode now keeps occupancy at Home until switched off instead of only saving a flag.

Backup & recovery is Owner-only. Configuration files use the `thermabot-config` format with
schema version 1; exports contain saved settings, never environment credentials. Unknown or
unsafe settings are rejected. Preview is read-only. Apply requires a stopped bot, a matching
preview fingerprint, and a verified pre-import SQLite backup. Import does not start the bot;
changing the thermostat still requires restart. A failed backup prevents import.

Database downloads include password hashes, sessions, household configuration and local data.
Keep encrypted off-device copies. Nightly backups retain seven daily files; manual/pre-import
copies require offline retention management. Home Assistant, environment secrets and InfluxDB
are separate backup responsibilities. The recovery screen documents integrity checking and
offline restore into an empty data directory with the HA enable mirror off. There is no live
database replacement route.

The downloadable HA package is optional and inert until configured and enabled. Review and
merge existing helpers; configure a private local webhook, verify minute heartbeats, and only
then enable its safety-net helper. After 15 minutes without heartbeat it disables the mirror
and raises an HA persistent notification. It never writes climate settings, restores an OFF
thermostat, or automatically resumes control. It cannot run during an HA outage. The existing
`deploy/ha/thermabot_watchdog.yaml` restore-from-OFF automation is a separate, explicitly
reviewed option, not something the app silently enables.

## Following priorities

After the SHADOW gate, continue the broader roadmap in this order: Home Assistant add-on as
the primary install path; desktop/mobile UAT and accessibility; backup/restore drills and
validated configuration import/export; staged PWA installability and offline read-only
behavior before opt-in notifications; then evaluate fan, cover, and supplemental climate
devices one class at a time behind explicit opt-in and SHADOW evaluation.

## Next-version discovery: devices, sunlight, floors and rooms

Owner-requested follow-on scope, explicitly excluded from the current UI/recovery release.
This is a discovery and design backlog, not authorization for the application to actuate
live equipment. No new fan, blind or heater controls ship in the current version.

The first next-version slice is included in v0.6.8-rc.3: the setup wizard reads HA home
coordinates/time zone and `sun.sun`, suggests fan/cover/heater/door entities, and lets the
Owner label confirmed rooms by floor. Owners can opt into a read-only contact assessment
with explicit room mapping, garage-to-house contact relationships, sustained-open thresholds,
and a closure stabilization delay. It never changes the comfort plan or actuates equipment.
Registry-backed floor/area discovery, solar-gain modeling, door-aware plan proposals, and
actuator control remain future work.

1. **Home Assistant discovery and solar context.** Use HA's configured home latitude,
   longitude and time zone rather than browser geolocation or assumed coordinates. Reuse
   the existing home-location lookup where appropriate; validate missing/invalid coordinates.
   Read HA's sun elevation and azimuth to establish current sun position. Assess window
   orientation, shading, room exposure and forecast solar gain before claiming a sun-aware
   comfort benefit. Keep household coordinates private.
2. **Floor/room assessment.** Inventory HA floors, areas, device/entity associations,
   thermostat zones and temperature/humidity sensors. Confirm the floor-to-room-to-sensor
   map with the Owner; do not infer reliable zoning from entity names alone. Assess upstairs
   versus downstairs stratification, room offsets, occupancy, sensor freshness/calibration,
   window exposure and which devices can actually affect each room. Preserve room-specific
   comfort bounds instead of optimizing only the central thermostat.
3. **Capability-aware temperature control.** Inspect supported HVAC modes, target-temperature
   versus heat/cool ranges, units, limits, resolution, fan modes and device availability.
   Distinguish whole-house HVAC, independently controlled zones and supplemental heaters;
   account for thermal lag and prevent competing heating/cooling or excessive cycling.
   Unsupported or stale devices must remain unavailable for automatic control.
4. **Additional actuators, one class at a time.** Evaluate ceiling fans first, then motorized
   blinds/covers and supplemental heaters. Fans primarily change perceived comfort, not room
   temperature; occupancy, humidity, noise and device speed support matter. Blinds need solar
   exposure, travel/position semantics, manual override and egress/privacy constraints.
   Heater automation requires suitable hardware with independent over-temperature/tip-over
   protection, explicit opt-in, bounded operation and fail-safe behavior; a generic smart
   plug is not sufficient evidence of safe unattended control.
5. **Open-door and garage-aware comfort.** Discover HA exterior-door contact sensors and
   garage-door position entities, then confirm which openings actually expose conditioned
   rooms/zones. An open garage door alone must not imply the house is open: account for
   whether the garage is conditioned and whether the connecting house door is open.
   Ignore brief passages using configurable open-duration thresholds; for sustained openings,
   evaluate a bounded setback or pause for the affected HVAC zone, with a visible explanation
   and optional held-open notification. Consider indoor/outdoor temperature and humidity,
   occupancy and equipment capabilities rather than indiscriminately switching the whole
   system off. Preserve freeze/overheat protection and equipment minimum run/off times.
   Unknown or stale contacts must not trigger an assumed-open shutdown. After confirmed
   closure and a stabilization delay, re-evaluate the current comfort plan and manual overrides
   instead of blindly restoring an old setpoint. Never close or lock a door automatically.
   Validate brief openings, sustained openings, sensor failures, garage/house-door combinations
   and closure recovery in SHADOW and UAT before opt-in live control. This remains future
   scope, not a change to the current release.
6. **Evidence before enablement.** Start with a read-only assessment and a reviewed device/
   floor/room map, then model proposals in SHADOW. Compare room/floor comfort and energy
   against the thermostat-only baseline. Exercise missing sensors, stale HA data, outages,
   restarts and manual overrides with mocks and controlled UAT. Require per-device Owner
   approval, safe fallback and measured benefit before any live actuation.

The next-version design should make room/floor conditions, solar influence and proposed
device actions understandable in both mobile and desktop UI. Do not assume compatible
equipment, adequate sensors, or an accurate floor plan until the assessment establishes them.
